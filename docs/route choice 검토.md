# 학습 데이터 검토 코멘트 검토 (2026.03.27)

---

## 1. 교수님 코멘트 요약

1. 퍼스트/라스트 마일 도보 데이터가 없어서 모형이 이상하게 나올 것 같다
2. H3 셀 단위로 학습데이터가 만들어진 게 아닌 것 같은데 다시 확인해야 한다
3. H3 셀 centroid 기반으로 OTP를 재쿼리하여 학습 데이터를 재구축해야 한다

---

## 2. 확인된 사실

### 2.1 OD 단위는 정류장-정류장

`tcn_to_otp_od.py`에서 승/하차정류장 좌표를 직접 OTP에 전달하여 경로를 생성하고 있으며, H3 셀 기반 처리는 현재 코드베이스에 없습니다.

학습 데이터의 경로(대안 셋)는 OTP의 Raptor 알고리즘으로 생성한 것이며, 스마트카드는 경로 생성이 아닌 선택확률(choice_prob) 산출에 사용됩니다. 즉, 학습 데이터의 피처는 Raptor가 탐색한 경로의 속성이고, 스마트카드는 그 중 어떤 경로가 실제로 선택되었는지를 매칭하는 데 사용됩니다.

학습과 모형 적용 모두 정류장 to 정류장 기준으로 수행했습니다. (영향권 분석은 그 존 내에 존재하는 OD들에 대해서 각각 구한 후 집계한 것입니다.)

### 2.2 도보 피처가 "거의 0"은 아님

도보 피처의 중앙값만 보면 낮지만, 전체 분포를 확인하면 의미 있는 값을 가진 대안이 상당수 존재합니다.

| 피처          | 중앙값 | 75%ile    | 평균  |
| ------------- | ------ | --------- | ----- |
| access_time   | 7초    | **125초** | 89초  |
| egress_time   | 9초    | **149초** | 97초  |
| walk_distance | 242m   | **482m**  | 301m  |
| walk_time     | 202초  | **402초** | 251초 |

OTP는 출발지가 정류장 좌표이더라도 해당 정류장에서만 탑승하는 경로만 반환하는 것이 아니라, 도보로 인근 지하철역이나 다른 정류장을 경유하는 경로도 함께 반환합니다.

| 지표                       | 값        |
| -------------------------- | --------- |
| access_time > 60초인 대안  | **32.8%** |
| access_time > 180초인 대안 | **19.4%** |

같은 OD 내에서 대안 간 도보 차이도 존재합니다:
ㄴ
| OD 내 access_time 변동 | 비율 |
|---|---|
| std == 0 (대안 간 차이 없음) | 41.8% |
| std > 60초 (유의미한 차이) | **42.5%** |
| std > 120초 (큰 차이) | **29.3%** |

도보 관련 컬럼을 학습 데이터에 포함시킨 것은, 가능한 많은 피처를 모형에 넣어 모형이 스스로 유의미한 변수를 선택할 수 있도록 하기 위함입니다.

## 3. H3 재구축에 대한 검토 의견

### 3.1 학습/적용 OD 단위 불일치 문제는 현재 존재하지 않음

현재 학습과 적용 모두 정류장 OD 단위로 수행하고 있어 불일치가 발생하지 않습니다.

과거에는 GTX 등 경로 계산 시간 문제로 zone(H3) 단위로 집계한 적이 있었으나, 현재는 Raptor 기반 OTP로 정류장 OD 단위 전수 계산이 가능해져 OD 단위로 전환한 상태입니다.

### 3.2 H3 전환 시 고려해야 할 사항

**(1) choice set의 동질성**

경로선택모형은 "동일한 선택 상황에서 어떤 대안을 선택했는가"를 전제로 합니다.

정류장 OD에서는 동일한 출발/도착 조건에서의 대안 비교이므로 이 전제가 성립합니다. H3 OD로 전환하면 OTP 대안은 centroid 한 점에서 생성되지만, SC 관측은 셀 내 서로 다른 정류장에서 출발한 통행들의 혼합이 됩니다.

대안 셋의 피처와 관측된 선택확률이 동일한 선택 상황을 반영하는지 확인이 필요합니다.

**(2) SC 매칭이 근본적으로 어려워짐**

현재 매칭이 가능한 이유는 OD와 SC의 출발 정류장이 같기 때문입니다:

```
현재 (정류장 OD):
  OTP: 정류장A → 버스100 → 정류장X    ← 같은 정류장 출발
  SC:  정류장A에서 버스100 탑승         ← 같은 정류장 출발
  → transit leg(정류장, 노선, 수단)이 일치 → 매칭 가능
```

H3로 전환하면 OTP는 centroid 위치 기준으로 가까운 정류장/노선 위주로 경로를 생성하지만, 셀 내 실제 이용자들은 각자 집 근처 정류장에서 탑승합니다:

```
H3 전환 시:
  OTP: centroid → 도보 → 정류장B → 버스200   ← centroid 기준 경로
  SC:  정류장A에서 버스100 탑승                ← 실제 이용자 경로
  → 출발 정류장도 다르고 노선도 달라 매칭 불가
```

유사도 매칭의 핵심인 mode, route, sequence가 전부 어긋나게 되어 매칭 자체가 성립하기 어렵습니다. H3 셀 안에는 여러 정류장과 노선이 존재하는데 OTP는 centroid 한 점에서 경로를 생성하므로, 셀 내 실제 통행의 상당수가 OTP 대안과 매칭되지 않을 가능성이 높습니다.

**(3) 도보 피처의 검증**

H3에서 도보 피처가 생성되지만 centroid라는 대표점에서 OTP가 계산한 값이며, SC 데이터는 승/하차 정류장만 기록하므로 실제 도보와의 대조 검증은 어렵습니다.

### 3.3 정류장 선택에 대해

현재 모형은 "정류장 쌍이 주어졌을 때 어떤 경로를 선택하는가"를 범위로 하며, 정류장 선택 자체는 모형 밖에 있습니다.

다만 OTP가 정류장 OD에서 출발하더라도 도보로 다른 정류장/지하철역을 경유하는 경로를 반환하고 있어, 42.5%의 OD에서 대안 간 access_time 차이가 존재합니다. 정류장 선택이 완전히 배제된 것은 아ㄴ니라고 생각을 했습니다.
